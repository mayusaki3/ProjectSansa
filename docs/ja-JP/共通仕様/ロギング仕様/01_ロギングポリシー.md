# ロギングポリシー（Project Sansa 共通）

## 1. 目的

本ドキュメントは、Project Sansa 全体で共通利用する  
**システムログ**および**監査ログ**の基本方針を定義する。

本ポリシーは以下を目的とする。

- 障害解析・運用監視・セキュリティ調査を可能にする
- サービス間で一貫したログ形式・判断基準を提供する
- 実装・テストで検証可能な仕様を先に確定する
- sansa-auth を含む全サービスで再利用可能な共通基盤とする

本仕様は **sansa-auth 専用ではない**。

---

## 2. 適用範囲

- Project Sansa に属するすべてのバックエンドサービス
  - sansa-auth
  - 今後追加される API / Web / XR / 管理サービス 等
- 開発環境・CI・本番環境すべてに適用する

---

## 3. ログ種別と役割分担

### 3.1 システムログ（System Log）

#### 目的
- 障害解析
- 運用監視
- 性能劣化・異常挙動の検出

#### 対象者
- 開発者
- 運用担当者

#### 特徴
- ログレベル（DEBUG / INFO / WARN / ERROR）を持つ
- スタックトレース出力を許可する
- 構造化ログ（JSON）を前提とする
- 後段で APM / SIEM / 集約基盤に投入可能な形式とする

---

### 3.2 監査ログ（Audit Log）

#### 目的
- 「誰が・何を・いつ・どこから行ったか」の追跡
- 不正検知・事後調査
- コンプライアンス対応

#### 対象者
- セキュリティ管理者
- 監査担当者

#### 特徴
- イベント単位で記録する（例：LOGIN_SUCCESS）
- 原則として追記専用
- スタックトレース等の内部実装情報は含めない
- 改ざん耐性を考慮する（詳細は 02_監査ログポリシー）

---

## 4. ログと例外の基本関係

### 4.1 例外分類

Project Sansa では、例外を以下に分類する。

- **ドメイン例外**
  - 想定内のビジネスエラー
  - 主に HTTP 4xx として応答
  - DomainException を基底とする
- **技術例外**
  - 想定外エラー（NPE、DB障害、通信障害など）
  - 主に HTTP 5xx として応答

---

### 4.2 DomainException 前提

- すべてのドメイン例外は DomainException を継承する
- DomainException は以下を保持する
  - error code（機械可読）
  - args（i18n / ログ補助情報）
- **例外の message フィールドはロジック・表示用途では使用しない**
  - message はログ用途に限定される

---

## 5. システムログ出力方針

### 5.1 出力責務

- 例外処理に伴うログ出力は **GlobalExceptionHandler に集約する**
- サービス層で個別にログレベル判断は行わない
- これによりログ方針を一箇所に固定する

---

### 5.2 ログレベル基準

| 区分 | 内容 | ログレベル |
|----|----|----|
| DomainException（4xx） | 想定内エラー | INFO または WARN |
| 技術例外（5xx） | 想定外エラー | ERROR |
| デバッグ用途 | 開発限定 | DEBUG / TRACE |

#### 補足
- 認証失敗、レート制限超過などセキュリティ寄りの 4xx は WARN とする
- 単純な入力不備は INFO でよい

---

### 5.3 スタックトレース出力

- DomainException
  - 原則として出力しない
  - DEBUG レベル時のみ出力可
- 技術例外
  - ERROR ログとして必ず出力する

---

### 5.4 システムログ最低必須項目

- timestamp（ISO8601 + timezone）
- level
- serviceId（例：sansa-auth）
- logger
- requestId
- userId（存在する場合）
- httpMethod
- path
- status（HTTP）
- exceptionCode（DomainException.code）
- exceptionClass（任意、デバッグ用途）

詳細な型定義は `03_ログスキーマ共通定義.md` に委ねる。

---

## 6. 監査ログ出力方針（概要）

- 監査ログは「例外の有無」ではなく「イベント結果」を主語にする
- 成功・失敗ともに、必要なイベントのみを記録する
- 例外コードは、監査イベント判定の判断材料として利用する

### 例
- InvalidCredentialsException
  - システムログ：WARN
  - 監査ログ：AUTH_LOGIN_FAILED
- TokenReusedException
  - システムログ：WARN または ERROR
  - 監査ログ：TOKEN_REUSE_DETECTED（必須）

詳細は `02_監査ログポリシー.md` に記載する。

---

## 7. 機微情報の取り扱い

以下の情報は **システムログ・監査ログともに出力禁止**。

- パスワード（平文・ハッシュ含む）
- 認証コード（メール、TOTP 等）
- アクセストークン／リフレッシュトークンの平文
- セッションIDの平文（必要な場合はハッシュ化）

IP アドレス・ User-Agent については

- システムログ：必要に応じて粗化
- 監査ログ：ハッシュ化必須

## 8. ログのライフサイクル管理（共通）

本章では、Project Sansa における  
ログ生成から保存・参照・廃棄までのライフサイクルを定義する。

---

### 8.1 ログライフサイクルの全体像

ログは以下の段階を経る。

1. 生成（Application）
2. 永続化（Primary Storage）
3. 参照 / 利用
4. Export（任意）
5. 廃棄（Retention 終了後）

ログ種別により、保存期間および取り扱いが異なる。

---

### 8.2 システムログのライフサイクル

#### 目的
- 障害解析
- 運用監視
- パフォーマンス調査

#### 保存先
- 各サービスのログ基盤（標準ログ出力 → 集約基盤）

#### 保存期間（目安）
- 本番環境：30〜90 日
- 開発 / CI：短期（数日〜数週間）

#### 廃棄方針
- 保持期間経過後、自動削除
- Export を前提としない

#### 特記事項
- システムログは「監査証跡」として扱わない
- 改ざん耐性（recordHash / signature）は必須ではない

#### 8.2.1 ローテーションと保持期間（重要）

システムログは監査ログと異なり、証跡としての永続性・完全性は要求されない。  
そのため、OS やログ基盤（logrotate / journald / CloudWatch Logs / ELK ILM 等）が提供する  
「ローテーション＋保持期間制御」を前提とする。

##### 推奨保持期間（デフォルト）

| 環境 | 推奨ローテーション | 推奨保持期間 |
|------|----------------------|--------------|
| production | 1日または1週間 | 30日前後 |
| staging | 1日 | 7〜14日 |
| development | 1日 | 1〜7日 |

**保持期間を過ぎたシステムログは自動削除される前提とする。**  
アプリケーション側が削除タイミング・容量制御を実装することは禁止する  
（環境依存であり、責務分離の観点から NG）。

##### 本仕様の位置づけ

- システムログは障害解析・運用監視が目的であり、  
  **長期保存・不変性保持は不要** と明確化する。
- 改ざん耐性（recordHash / signature）は **監査ログのみに適用し、システムログには適用しない**。
- ローテーション戦略はサービス共通の推奨であり、  
  実運用ではインフラチームが環境ごとに最適化してよい。

##### テスト方針

- ログ削除（保持期間終了）やローテーションは OS / ログ基盤の責務であるため **UT / IT ではテスト対象外** とする。
- システムログのテスト対象は以下に限定する：
  - 正しいログレベルで出力されること
  - 禁止情報（パスワード・トークン）が含まれないこと
  - JSON 形式が仕様どおりであること

---

### 8.3 監査ログのライフサイクル

#### 目的
- セキュリティ監査
- 不正検知
- 事後調査
- 説明責任の確保

#### 保存先（正本）
- Cassandra（Project Sansa 共通）

#### 保存期間
- 原則：長期保存（年単位）
- 正確な年数は運用ポリシーに依存

#### 改ざん耐性
- 本番環境では以下を必須とする
  - recordHash
  - previousHash
  - signature
  - keyId

#### Export
- 定期的な Export（CSV / Parquet 等）を許容
- Export データは分析・調査用途に使用可能
- Export 後も Cassandra 上の正本は削除しない

#### 廃棄
- 廃棄は原則「論理的廃棄」とする
- コンプライアンス要件が発生した場合のみ
  - 物理削除 / WORM アーカイブへの移行を検討する

---

### 8.4 環境別の扱い

| 環境 | 監査ログ | recordHash / signature |
|----|----|----|
| 本番 | 必須 | 必須 |
| 開発 | 保存 | 任意（原則生成） |
| CI | 保存不要 / 最小限 | 任意 |

---

### 8.5 本仕様と将来拡張

- 本仕様では WORM Storage を必須としない
- 将来、法的・コンプライアンス要件が明確になった場合
  - Export + WORM 保存を追加する
- その場合も Cassandra 上の監査ログを一次正本とする方針は維持する
