# リポジトリ・ドメインモデル仕様（Project Sansa / sansa-auth）

## 1. 目的

本書は sansa-auth における **ドメインモデル** および  
それらを永続化する **Repository Port（インターフェース）** の仕様を定義する。

API仕様（01_ユーザー登録.md / 02_ログイン.md / 04_MFA.md / 05_セッション管理.md など）と整合した形で、  
サービス層（AuthService / MfaService / SessionService など）が依存する I/F を明文化し、  
以下を目的とする。

- 実装差し替え（inmem / Cassandra など）時に破綻しない境界の確立
- サービス実装のテスト容易性向上（Repository をモックしやすくする）
- 将来的なスキーマ変更時に、影響範囲を把握しやすくする

対象となるドメイン/Repository は以下とする。

- User / UserRepository
- PreRegistration / PreRegistrationRepository
- Session / SessionRepository
- RefreshToken / RefreshTokenRepository
- TotpSecret / TotpSecretRepository
- RecoveryCode / RecoveryCodeRepository

## 2. 共通ルール

### 2.1 型・ID・日時

- ID はすべて `String`（UUID 文字列など）で扱う
  - 例: userId, sessionId, preRegId, token など
- 日時は `java.time.Instant` を使用する
  - DB 側では TIMESTAMP WITH TIME ZONE 等にマッピング
- null を返す代わりに `java.util.Optional` を使用する
  - Repository の戻り値で「存在しない可能性がある」場合は `Optional<T>` とする

### 2.2 例外・エラー扱い

- Repository は **基本的にドメインレベルの例外を投げない**
  - 主な責務は「存在する/しない」「一意制約違反」などの永続化層の結果を返すこと
- ただし、以下は例外として許容する
  - 引数が不正（null / 空文字など）で明らかにバグである場合 → `IllegalArgumentException`
  - DB 接続エラーなどのインフラ障害 → 実装側で適切な RuntimeException にラップ

### 2.3 トランザクション

- トランザクション境界は **サービス層**（AuthServiceImpl 等）で管理する前提とし、  
  Repository 単体ではトランザクション境界を意識しない。
- ただし、「複数レコードをまとめて扱うメソッド」は  
  サービス層が 1 トランザクション内で呼び出す前提で設計する。
  - 例: RecoveryCode の `insertAll` と `deleteAllByUserId` を同一トランザクションで呼ぶ、など

### 2.4 inmem / Cassandra 実装方針

- `spring.profiles.active=inmem` では、簡易な in-memory 実装を用意する
  - Map や ConcurrentHashMap を使った実装でよい
  - API仕様に対する動作確認用・UT/IT 用
- Cassandra 実装（将来実装を想定）は、同一インターフェースを満たす
  - テーブル構成やインデックス戦略の違いは実装側に閉じ込める

## 3. User / UserRepository

### 3.1 ドメインモデル: User

#### 3.1.1 概要

- 認証対象ユーザーのドメインモデル
- パスワードログイン、メール検証状態、トークンバージョンなどを保持する
- MFA の詳細（TOTP 秘密鍵・リカバリーコードなど）は別モデルで管理する

#### 3.1.2 フィールド

- `id: String`  
  ユーザーID（UUID）

- `identifier: String`  
  ログインID（メールアドレスまたは任意のユーザー名）

- `email: String`  
  通知・MFA 用メールアドレス

- `passwordHash: String`  
  パスワードハッシュ（PasswordPort で生成）

- `emailVerified: boolean`  
  メールアドレスが検証済みかどうか

- `mfaEnabled: boolean`  
  MFA が有効かどうか（TOTP/Email/Recovery の有効状態は別途参照）

- `tokenVersion: int`  
  トークンバージョン（tv）。全失効（ログアウト ALL）時にインクリメントする。

- `createdAt: Instant` / `updatedAt: Instant`  
  作成・更新日時

### 3.2 Repository: UserRepository

#### 3.2.1 役割

- User エンティティの CRUD を提供する
- AuthServiceImpl の以下ユースケースから利用される想定
  - ログイン時: identifier / email での検索
  - パスワード変更時: passwordHash + tokenVersion の更新
  - メール検証完了時: emailVerified の更新

#### 3.2.2 メソッド仕様

1. `Optional<User> findById(String userId)`

   - 入力
     - `userId`: ユーザーID（必須・空文字不可）
   - 動作
     - userId に一致するユーザーが存在すれば返す
   - 事後条件
     - 存在しない場合は `Optional.empty()`

2. `Optional<User> findByEmail(String email)`

   - 入力: `email`（必須）
   - 目的: メールアドレスをキーにユーザー取得
   - ユースケース: メール検証・MFA メール送信など

3. `Optional<User> findByIdentifier(String identifier)`

   - 入力: `identifier`（必須）
   - 目的: ログインIDをキーにユーザー取得
   - ユースケース: `/auth/login` の認証前処理

4. `User insert(User user)`

   - 入力: 新規ユーザー（id が未設定でもよい）
   - 動作: 新規レコードを挿入し、ID 等を付与して返す
   - エラー:
     - 同一 identifier/email の一意制約違反 → RuntimeException（実装依存）

5. `User update(User user)`

   - 一般的な更新用メソッド
   - 事後条件: 該当レコードが存在しない場合の扱いは実装依存（通常は例外）

6. `void updatePasswordAndTokenVersion(String userId, String newPasswordHash, int newTokenVersion, Instant now)`

   - 用途: パスワード変更時に、passwordHash と tokenVersion を一括更新
   - ユースケース:
     - パスワード変更に伴い、既存トークンを tv で無効化する

7. `void updateEmailVerified(String userId, boolean verified, Instant now)`

   - 用途: verify-email 完了時に emailVerified を true にする

## 4. PreRegistration / PreRegistrationRepository

### 4.1 ドメインモデル: PreRegistration

#### 4.1.1 概要

- ユーザー登録前の「メールアドレス事前登録」情報
- 01_ユーザー登録.md の
  - `/auth/register/pre-register`（メール送信）
  - `/auth/register/verify-email`
  - `/auth/register`  
  に対応する内部状態を保持する。

#### 4.1.2 フィールド

- `preRegId: String`  
  事前登録ID（UUID）

- `email: String`  
  登録メールアドレス

- `language: String`  
  希望表示言語（ja-JP 等）

- `verifyCodeHash: String`  
  メールで送信する検証コードのハッシュ

- `createdAt: Instant` / `expiresAt: Instant`  
  作成日時・有効期限

- `verifiedAt: Instant` (nullable)  
  verify-email 成功日時

- `completedAt: Instant` (nullable)  
  register 成功日時

### 4.2 Repository: PreRegistrationRepository

#### 4.2.1 メソッド仕様

1. `PreRegistration insert(PreRegistration preReg)`

   - 新規 preReg を登録する
   - 一意制約（同一 email の重複）等の扱いは実装に委ねる

2. `Optional<PreRegistration> findById(String preRegId)`

   - preRegId から事前登録情報を取得する
   - ユースケース
     - verify-email / register 両方

3. `void markVerified(String preRegId, Instant verifiedAt)`

   - verify-email 成功時に `verifiedAt` をセット
   - 冪等に扱える実装が望ましい（2 回目の呼び出しでエラーにしない）

4. `void markCompleted(String preRegId, Instant completedAt)`

   - register 成功時に `completedAt` をセット

5. `void deleteExpired(Instant now)`

   - 実装側でバッチ等から呼び出す前提のメソッド
   - `expiresAt < now` のレコードを削除する

## 5. Session / SessionRepository

### 5.1 ドメインモデル: Session

#### 5.1.1 概要

- ログインセッション（/sessions API で参照する対象）
- アクセストークンとは別に、サーバ側で保持するセッション単位の情報

#### 5.1.2 フィールド

- `sessionId: String`  
  セッションID（UUID）。トークン内の `sid` に対応。

- `userId: String`  
  所有ユーザーID

- `userAgent: String`  
  クライアントの User-Agent 文字列（任意）

- `ipAddress: String`  
  アクセス元 IP アドレス（任意）

- `createdAt: Instant`  
  セッション開始日時

- `lastAccessAt: Instant`  
  最終アクセス日時

- `revokedAt: Instant` (nullable)  
  ログアウト/失効日時（null ならアクティブ）

### 5.2 Repository: SessionRepository

#### 5.2.1 メソッド仕様

1. `Session insert(Session session)`

   - 新しいセッションを作成
   - AuthServiceImpl が login 成功時に呼び出す

2. `Optional<Session> findById(String sessionId)`

3. `List<Session> findActiveByUserId(String userId)`

   - `/sessions` API で使用
   - `revokedAt == null` のものを返す

4. `void updateLastAccessAt(String sessionId, Instant lastAccessAt)`

   - アクセス毎に更新（必要であれば）

5. `void revoke(String sessionId, Instant revokedAt)`

   - 単一セッションのログアウト

6. `void revokeAllByUserId(String userId, Instant revokedAt)`

   - `/auth/logout`（tv ルールと併用）や `/sessions` からの「全セッションログアウト」で使用

## 6. RefreshToken / RefreshTokenRepository

### 6.1 ドメインモデル: RefreshToken

#### 6.1.1 概要

- リフレッシュトークンの追跡・ブラックリスト管理用
- TokenFacadeImpl が内部的に使用する

#### 6.1.2 フィールド

- `token: String`  
  リフレッシュトークン文字列（またはハッシュ）

- `userId: String`  
  所有ユーザーID

- `tokenVersion: int`  
  発行時点の tv（User.tokenVersion）

- `sessionId: String` (任意/推奨)  
  対応する Session の ID（セッション単位での追跡用）

- `issuedAt: Instant` / `expiresAt: Instant`  
  発行日時・有効期限

- `blacklistedAt: Instant` (nullable)  
  ブラックリスト入り日時

### 6.2 Repository: RefreshTokenRepository

1. `RefreshToken insert(RefreshToken token)`

2. `Optional<RefreshToken> findByToken(String token)`

3. `void blacklist(String token, Instant blacklistedAt)`

   - ローテーションや明示的ログアウト時に呼び出す

4. `void deleteExpired(Instant now)`

   - 期限切れ・古いトークンのクリーンアップ

## 7. TotpSecret / TotpSecretRepository

### 7.1 ドメインモデル: TotpSecret

#### 7.1.1 概要

- ユーザーごとの TOTP 秘密鍵
- MfaServiceImpl の `totpEnroll` / `totpActivate` / `totpVerify` から利用される

#### 7.1.2 フィールド

- `id: String`  
  TOTP レコードID（UUID）

- `userId: String`  
  ユーザーID

- `secret: String`  
  TOTP 秘密鍵（Base32 等）

- `active: boolean`  
  有効フラグ

- `createdAt: Instant` / `activatedAt: Instant` / `deactivatedAt: Instant` (nullable)

### 7.2 Repository: TotpSecretRepository

1. `TotpSecret insert(TotpSecret secret)`

   - enroll 時に呼び出す

2. `Optional<TotpSecret> findActiveByUserId(String userId)`

   - verify / 再発行などで利用

3. `void activate(String id, Instant activatedAt)`

   - 指定レコードを有効化

4. `void deactivateAllByUserId(String userId, Instant deactivatedAt)`

   - 再発行や TOTP 無効化時に使用

---

## 8. RecoveryCode / RecoveryCodeRepository

### 8.1 ドメインモデル: RecoveryCode

#### 8.1.1 概要

- MFA 用リカバリーコード
- MfaServiceImpl の `recoveryIssue` / `recoveryVerify` で利用される

#### 8.1.2 フィールド

- `id: String`  
  コードID（UUID）

- `userId: String`  
  ユーザーID

- `codeHash: String`  
  リカバリーコードのハッシュ

- `issuedAt: Instant`  
  発行日時

- `usedAt: Instant` (nullable)  
  使用日時

### 8.2 Repository: RecoveryCodeRepository

1. `void insertAll(List<RecoveryCode> codes)`

   - 発行時に複数件まとめて登録

2. `List<RecoveryCode> findAllByUserId(String userId)`

   - `/auth/mfa/recovery/issue` のレスポンス生成時、  
     既存コードとの重複確認や再発行などに利用

3. `Optional<RecoveryCode> findUnusedByUserIdAndCodeHash(String userId, String codeHash)`

   - verify 時に「未使用のコードか」を判定する

4. `void markUsed(String id, Instant usedAt)`

   - 使用済みにする

5. `void deleteAllByUserId(String userId)`

   - 再発行時に古いコードを削除する

## 9. サービス層との対応関係（概要）

本書で定義した Repository は、サービス層から以下のように利用される想定である。

- AuthServiceImpl
  - UserRepository（ログイン・登録後のユーザー作成/更新）
  - PreRegistrationRepository（事前登録フロー）
  - SessionRepository（ログイン成功時のセッション作成 / ログアウト）
  - RefreshTokenRepository（TokenFacade 経由）
- MfaServiceImpl
  - UserRepository（ユーザー状態参照）
  - TotpSecretRepository（TOTP enroll/activate/verify）
  - RecoveryCodeRepository（recovery issue/verify）
  - RefreshTokenRepository + SessionRepository（MFA 成功後のトークン再発行・セッション更新）

サービス層の I/F 仕様は、別途「サービスポート仕様（AuthService/MfaService/SessionService）」にて定義する。
