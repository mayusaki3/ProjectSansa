# サービスポート仕様（Project Sansa / sansa-auth）

## 1. 目的

本書は sansa-auth における **サービスポート（Service / Port インターフェース）** の仕様を定義する。

- コントローラー層（AuthController / MfaController / SessionController 等）から見た境界
- リポジトリ・ドメインモデル仕様:contentReference[oaicite:0]{index=0} と API仕様（01_ユーザー登録.md / 02_ログイン.md / 04_MFA.md / 05_セッション管理.md 等）:contentReference[oaicite:1]{index=1} の橋渡し

を明文化し、以下を目的とする。

- 実装差し替え（inmem / Cassandra 等）時に破綻しない境界の確立
- サービス実装のテスト容易性向上（Port をモックしやすくする）
- API仕様・リポジトリ仕様・サービス実装の三者の整合確認を容易にする
- 「実装し直し」による破綻を防ぎ、インターフェースの安定性を高める

対象サービスポートは以下とする。

- `AuthService`（ログイン・ユーザー登録・ログアウト・リフレッシュ等）
- `MfaService`（TOTP / Email OTP / Recovery Code 等の MFA 全般）
- `SessionService`（セッション一覧 / 削除 / ログアウト）
- `PasswordPort`（パスワードハッシュ生成・検証の抽象化）
- `TokenFacade`（アクセストークン・リフレッシュトークンの発行・ローテーション・ブラックリスト管理）

## 2. 共通ルール

### 2.1 呼び出し元と責務分担

- 呼び出し元は原則として **コントローラー層**（REST Controller）とする
  - 例: `AuthController` → `AuthService`
  - 例: `MfaController` → `MfaService`
  - 例: `SessionController` → `SessionService`
- サービスポートは以下を責務とする
  - 入力 DTO のバリデーション（API仕様に沿ったビジネスルール）
  - リポジトリ Port の呼び出し・トランザクション管理
  - ドメインイベント（トークン発行・メール送信・MFA 状態変化等）の整合性確保
- コントローラー層は以下に責務を限定する
  - HTTP リクエスト → DTO 変換
  - サービスポートの呼び出し
  - サービスポートが投げる例外を ProblemDetail などにマッピング

### 2.2 例外方針

サービスポートは、リクエストの妥当性や認可に関して **ドメイン例外** を投げる。

- クライアント入力不正（バリデーション違反）
  - 例: 必須項目欠落・フォーマット不正・期限切れコード等
  - → `BadRequestException`（HTTP 400）
- 認証・認可エラー
  - 例: 認証されていない / トークン無効 / セッション不整合等
  - → `UnauthorizedException` または `ForbiddenException`（HTTP 401/403）
- リソース不在
  - 例: 対象ユーザー・セッションが存在しない
  - → 必要に応じて `NotFoundException`（導入済み/未導入は実装に従う）
- それ以外の予期しないエラー
  - → ラップされた RuntimeException（HTTP 500）

Controller とのマッピングは API仕様（エラー仕様・ProblemDetail）側で定義し、本書では「どの例外を投げるか」までを範囲とする。

#### 例外設計との関係

本インターフェースで送出される例外は、
原則として以下のドキュメントに従う。

- [例外・エラー設計ポリシー](03_例外・エラー設計ポリシー.md)
- [例外クラス一覧](04_例外クラス一覧.md)

本インターフェースの実装は、
- 技術例外（DB / トークン / メール等）をそのまま外へ漏出させない
- サービス層でドメイン例外へマッピングすること
を前提とする。

### 2.3 DTO と戻り値

- 入力・出力は原則として **API仕様側で定義される DTO** をそのまま使用する
  - 例: `LoginRequest` / `LoginResponse`
  - 例: `MfaTotpEnrollRequest` / `MfaTotpEnrollResponse` 等
- 本書では、DTO の詳細構造は API仕様に委ね、クラス名（または「ログインリクエストDTO」等の記述）で参照するに留める

### 2.4 トランザクション境界

- トランザクションの境界は **サービスポート実装**（`*ServiceImpl` / `TokenFacadeImpl`）側で管理する前提とする
- 代表例:
  - ログイン成功時:
    - UserRepository からユーザー取得
    - PasswordPort によるパスワード検証
    - SessionRepository によるセッション作成
    - TokenFacade によるトークン発行
    - → これらは 1 トランザクション内で完結させる
  - MFA 成功時:
    - MFA 情報検証（TOTP / Email OTP / Recovery Code）
    - 必要であれば MFA 状態更新（TOTP 有効化 / Recovery Code 使用済み）
    - TokenFacade によるトークン再発行（amr 更新）
    - → これも 1 トランザクション内で完結

### 2.5 セキュリティコンテキスト

- 認証済みユーザーの `userId`, `amr`, `sid` 等は、Spring Security 等の認証コンテキストから取得される
- サービスポートの引数として `userId` / `sessionId` を受け取る場合は、
  - 原則として「検証済みのコンテキスト値」を前提とし、
  - 不正な値の混入（他人の userId 指定等）は上位層で防ぐ設計とする

## 3. AuthService ポート仕様

### 3.1 役割

- 01_ユーザー登録.md / 02_ログイン.md で定義される **認証・登録フロー全般** のユースケースを提供する。
- 主な責務:
  - メール事前登録（pre-register）
  - メール検証（verify-email）
  - 本登録（register）
  - ログイン（password + 必要に応じて MFA チャレンジ生成）
  - トークンリフレッシュ（refresh）
  - ログアウト（logout）
  - セッション情報との連携（SessionService との分担は後述）

### 3.2 主なメソッド（概要）

ここではメソッド名・入出力の概略のみを示す。詳細な DTO 構造・HTTP ステータスは API仕様を参照する。

1. メール事前登録

   - シグネチャ例（イメージ）  
     `void preRegister(PreRegisterRequest req)`
   - 対応 API: `POST /auth/register/pre-register`
   - 責務:
     - PreRegistrationRepository へのレコード作成
     - 検証コードの生成・ハッシュ化
     - メール送信（MailService / SmtpMailService 連携）
   - 主な例外:
     - `BadRequestException`（既に登録済みメール等）

2. メール検証

   - `void verifyEmail(VerifyEmailRequest req)`
   - API: `POST /auth/register/verify-email`
   - 責務:
     - PreRegistrationRepository から対象 preReg を取得
     - 検証コードハッシュの照合
     - 期限切れチェック
     - `verifiedAt` の更新

3. 本登録

   - `RegisterResponse register(RegisterRequest req)`
   - API: `POST /auth/register`
   - 責務:
     - PreRegistration の状態確認（verified 済みか）
     - UserRepository へのユーザー作成
     - PasswordPort による passwordHash 生成
     - tokenVersion 初期値設定
     - 必要に応じて自動ログイン（LoginResponse 返却）など

4. ログイン

   - `LoginResponse login(LoginRequest req)`
   - API: `POST /auth/login`
   - 責務:
     - UserRepository から identifier/email でユーザー取得
     - PasswordPort によるパスワード照合
     - MFA 要否判定（User.mfaEnabled, amr 等）
     - 必要に応じて MFA チャレンジ用の情報発行（MfaService に委譲も可）
     - MFA 不要な場合は SessionRepository + TokenFacade によりトークン発行

5. リフレッシュトークンによる再発行

   - `LoginResponse refresh(RefreshRequest req)`
   - API: `POST /auth/refresh`
   - 責務:
     - TokenFacade によるリフレッシュトークン検証・ローテーション
     - UserRepository / SessionRepository を参照し、tv やセッション状態の整合性確認
     - 新しい Access/Refresh Token 発行

6. ログアウト（現在セッション）

   - `void logoutCurrent(LogoutCurrentRequest req)`
   - API: `POST /auth/logout`（tv ルールとの対応は仕様に従う）
   - 責務:
     - userId / sessionId をコンテキストから取得
     - tv インクリメント or RefreshToken ブラックリスト化
     - SessionRepository で現在セッション revoke

7. ログアウト（全セッション）

   - `void logoutAll(LogoutAllRequest req)`
   - API: `/auth/logout/all` 等（API仕様の有無に従う）
   - 責務:
     - User.tokenVersion のインクリメント
     - SessionRepository.revokeAllByUserId による一括 revoke
     - RefreshTokenRepository 側での一括無効化（tv による）

## 4. MfaService ポート仕様

### 4.1 役割

- 04_MFA.md で定義される **多要素認証フロー** を提供する。  
  - TOTP（Time-based One-Time Password）
  - Email OTP（メール認証コード）
  - Recovery Code（バックアップコード）

- AuthService と協調し、ログインフロー中の「2 段階目」として動作する。

### 4.2 インターフェース（B案）との対応

ユーザーから提示された B案インターフェース（`MfaService`）に基づき、本仕様を定める。

1. `MfaTotpEnrollResponse totpEnroll()`

   - API: `POST /auth/mfa/totp/enroll`
   - コンテキスト: 認証済み userId 必須
   - 責務:
     - 新しい TOTP 秘密鍵の生成
     - TotpSecretRepository.insert による登録
     - QRコード情報・シークレット文字列等をレスポンスに含める
   - 例外:
     - `UnauthorizedException`（未ログイン）
     - `BadRequestException`（すでにアクティブな TOTP が存在し enroll 不可 等）

2. `void totpActivate(MfaTotpActivateRequest req)`

   - API: `POST /auth/mfa/totp/activate`
   - 責務:
     - 入力された TOTP コードを検証
     - 正しければ TotpSecretRepository.activate / deactivateAllByUserId 等で有効化
     - User.mfaEnabled の更新（必要に応じて AuthService/AuthRepository 経由）

3. `LoginResponse totpVerify(MfaTotpVerifyRequest req)`

   - API: `POST /auth/mfa/totp/verify`
   - 責務:
     - TOTP コード検証
     - 成功時: `TokenFacade.issueAfterAuth` を利用し、amr に `mfa` 等を追加したトークンを再発行
     - 必要なら SessionRepository でセッション情報更新

4. `void emailSend(MfaEmailSendRequest req)`

   - API: `POST /auth/mfa/email/send`
   - 責務:
     - Email OTP（ワンタイムコード）生成
     - ハッシュ保存（専用 Repository または RefreshToken/PreRegistration 拡張で管理）
     - メール送信

5. `LoginResponse emailVerify(MfaEmailVerifyRequest req)`

   - API: `POST /auth/mfa/email/verify`
   - 責務:
     - メールコード検証・期限確認
     - 成功時: `TokenFacade.issueAfterAuth` 経由でトークン再発行

6. `MfaRecoveryIssueResponse recoveryIssue()`

   - API: `POST /auth/mfa/recovery/issue`
   - 責務:
     - RecoveryCode の複数件生成・ハッシュ化
     - RecoveryCodeRepository.insertAll で保存
     - 旧コード deleteAllByUserId で削除
     - 発行済みコード一覧をレスポンスとして返却（平文/マスクは仕様に従う）

7. `LoginResponse recoveryVerify(MfaRecoveryVerifyRequest req)`

   - API: `POST /auth/mfa/recovery/verify`
   - 責務:
     - RecoveryCodeRepository.findUnusedByUserIdAndCodeHash で検証
     - 成功時: markUsed で使用済みに
     - `TokenFacade.issueAfterAuth` でトークン再発行

## 5. SessionService ポート仕様

### 5.1 役割

- 05_セッション管理.md で定義される **セッション一覧・削除・ログアウト API** を提供する。
- SessionRepository と User/Token 状態を結びつけるドメインサービス。

提示された `SessionService` インターフェースに基づき仕様を整理する。

### 5.2 メソッド概要

1. `Optional<SessionInfo> getCurrentSession(String userId)`

   - API: `/sessions/me` 等（仕様に従う）
   - 責務:
     - コンテキストの sessionId / userId から現在セッション情報を取得
     - SessionRepository.findById / findActiveByUserId を使用

2. `List<SessionInfo> listSessions(String userId)`

   - API: `GET /sessions`
   - 責務:
     - `SessionRepository.findActiveByUserId` を呼び出し、DTO に詰め替え

3. `LogoutResponse deleteById(String userId, String sessionId)`

   - API: `DELETE /sessions/{sessionId}`
   - 責務:
     - 対象セッションが userId の所有か確認
     - `SessionRepository.revoke` で revoke
     - TokenFacade/RefreshTokenRepository 側で対象セッション由来トークンを無効化（必要に応じて）

4. `void logoutCurrentSession(String userId)`

   - API: `POST /auth/logout` の内部で利用（現在セッションのみログアウト等）
   - 責務:
     - コンテキストの sessionId に対して revoke

5. `void logoutBySessionId(String userId, String sessionId)`

   - API: `/sessions/{sessionId}/logout` のようなバリアントに対応可能
   - 責務:
     - deleteById とほぼ同様だが、戻り値が不要な場合のバリエーション

## 6. PasswordPort 仕様

### 6.1 役割

- パスワードハッシュ生成・検証ロジックを抽象化する Port。
- 実装（`PasswordPortImpl`）では、BCrypt / Argon2 等の具体的アルゴリズムに依存する。

### 6.2 主なメソッド（イメージ）

- `String hash(String rawPassword)`
  - 入力: 平文パスワード
  - 出力: ハッシュ文字列
  - 例外:
    - `IllegalArgumentException`（null / 空文字など）
- `boolean matches(String rawPassword, String encodedPassword)`
  - 用途: ログイン時のパスワード検証
  - 注意:
    - 時間差攻撃を避けるため、実装側で constant-time 比較を行う

### 6.3 利用箇所

- AuthServiceImpl の
  - 登録時: hash → User.passwordHash に保存
  - ログイン時: matches で検証
  - パスワード変更時: hash + User.tokenVersion インクリメント

## 7. TokenFacade 仕様

### 7.1 役割

- アクセストークン / リフレッシュトークンの発行・ローテート・ブラックリスト登録を抽象化する Facade Port。
- AuthServiceImpl / MfaServiceImpl から利用される。

提示された `TokenFacade` インターフェースに基づき仕様を整理する。

### 7.2 DTO 内部クラス

- `TokenFacade.Tokens`
  - `accessToken: String`
  - `refreshToken: String`
  - `sessionId: String`
- `TokenFacade.RotateResult`
  - `newRefreshToken: String`
  - `rotatedAt: Instant`

### 7.3 メソッド仕様

1. `Tokens issueTokens(String userId, int tokenVersion, Instant now, Duration accessTtl, Duration refreshTtl, String sessionId, List<String> amr)`

   - 用途:
     - ログイン成功時のトークン発行
   - 責務:
     - JWT 等による AccessToken の生成（`sub`, `tv`, `sid`, `amr` 等を含む）
     - RefreshToken の生成・保存（RefreshTokenRepository.insert）
   - 注意:
     - `tokenVersion` は User.tokenVersion と一致させる
     - `amr` は認証手段のリスト（password / mfa 等）

2. `RotateResult rotateRefreshToken(String refreshToken, Instant now)`

   - 用途:
     - `/auth/refresh` でリフレッシュトークンをローテーションする
   - 責務:
     - RefreshTokenRepository.findByToken で取得
     - 期限切れ・ブラックリスト・tv 不整合等の検証
     - 旧トークンを blacklist
     - 新トークンを発行・保存

3. `void blacklistRefreshToken(String refreshToken, Instant now)`

   - 用途:
     - ログアウト / セッション無効化時の明示的ブラックリスト登録

4. `Tokens issueAfterAuth(String userId, List<String> amr)`

   - 用途:
     - MFA 成功直後に、追加された `amr` を反映したトークン再発行
   - 挙動:
     - 既存の tv / セッション情報を維持しつつ、`amr` のみ拡張
     - `MfaService` からのみ呼ばれる想定

## 8. Controller / サービスポート / Repository 対応表（概要）

### 8.1 Controller → サービスポート

- `AuthController`
  - `/auth/register/pre-register` → `AuthService.preRegister(...)`
  - `/auth/register/verify-email` → `AuthService.verifyEmail(...)`
  - `/auth/register` → `AuthService.register(...)`
  - `/auth/login` → `AuthService.login(...)`
  - `/auth/refresh` → `AuthService.refresh(...)`
  - `/auth/logout` → `AuthService.logoutCurrent(...)` or `SessionService.logoutCurrentSession(...)` を内部で使用
- `MfaController`
  - `/auth/mfa/totp/enroll` → `MfaService.totpEnroll()`
  - `/auth/mfa/totp/activate` → `MfaService.totpActivate(...)`
  - `/auth/mfa/totp/verify` → `MfaService.totpVerify(...)`
  - `/auth/mfa/email/send` → `MfaService.emailSend(...)`
  - `/auth/mfa/email/verify` → `MfaService.emailVerify(...)`
  - `/auth/mfa/recovery/issue` → `MfaService.recoveryIssue()`
  - `/auth/mfa/recovery/verify` → `MfaService.recoveryVerify(...)`
- `SessionController`
  - `/sessions` / `/sessions/{id}` 系 → `SessionService.listSessions(...)`, `SessionService.deleteById(...)` 等

### 8.2 サービスポート → Repository（抜粋）

- `AuthService`
  - `UserRepository`
  - `PreRegistrationRepository`
  - `SessionRepository`
  - `RefreshTokenRepository`（TokenFacade 経由）
- `MfaService`
  - `UserRepository`
  - `TotpSecretRepository`
  - `RecoveryCodeRepository`
  - `RefreshTokenRepository` / `SessionRepository`（TokenFacade 経由）
- `SessionService`
  - `SessionRepository`
  - 必要に応じて `UserRepository`, `RefreshTokenRepository`

（詳細な Repository 仕様は「01_リポジトリ・ドメインモデル仕様」を参照）:contentReference[oaicite:2]{index=2}

## 9. 今後の拡張・検討メモ

- PasswordPort / TokenFacade は、将来的に sansa-auth 以外のモジュールでも利用される可能性があるため、
  - パッケージ配置（共通モジュール化）、
  - アルゴリズム変更（パスワードハッシュ・JWT 署名方式等）の影響範囲
  を別途ドキュメント化する余地がある。
- サービスポート仕様とテストポリシー（00_テストポリシー.md）を紐付けるため、
  - 「UT：サービス単体（Repository モック）」、
  - 「IT：Repository 実装込み（inmem / Cassandra）」、
  - 「E2E：API 経由（実サーバ起動）」  
  の粒度で、どのメソッドをどこまでカバーするか、マトリクスへの反映を行う。
- 例外設計については、「[例外・エラー設計ポリシー](03_例外・エラー設計ポリシー.md)」および「[例外クラス一覧](04_例外クラス一覧.md)」を正とし、
  本仕様に記載する各メソッドの throws はそれらの方針に従うこと。
