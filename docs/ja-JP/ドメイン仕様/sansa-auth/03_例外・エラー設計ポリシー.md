# 例外・エラー設計ポリシー（Project Sansa / sansa-auth）

## 1. 目的

この文書は、sansa-auth モジュールにおける例外・エラー処理の設計方針を定義する。

- コントローラー層（API仕様）
- サービス層（各サービスポート仕様）
- リポジトリ層・インフラ層

の間で一貫したエラー挙動を保証し、

- HTTP レスポンスの統一
- ログ出力・監視の一貫性
- 実装差し替え時（inmem → Cassandra 等）における挙動の安定

を目的とする。

## 2. スコープ

本ポリシーは、以下を対象とする。

- sansa-auth 内の全 REST API（/auth/* /sessions* /webauthn* /auth/mfa* 等）
- サービスインターフェース（AuthService, MfaService, SessionService, WebAuthnService など）
- サービスポート（PasswordPort, TokenFacade, 各 Repository Port など）
- 例外ハンドリング用の共通クラス（例: GlobalExceptionHandler 相当）

他モジュール（例: 別サービスの認証）で本ポリシーを流用する場合は、本書をベースに必要に応じて拡張する。

## 3. 例外クラスの分類

### 3.1 レイヤ別の例外分類

1. 入力バリデーション（コントローラー層）
   - Bean Validation 由来の例外  
     - MethodArgumentNotValidException  
     - ConstraintViolationException 等
   - JSON 解析エラー（HttpMessageNotReadableException 等）

2. 認証・認可エラー
   - Unauthorized（未ログイン・認証失敗）  
   - Forbidden（権限不足・AMR 不足など）

3. ドメインエラー（クライアント起因の業務エラー）
   - BadRequestException
   - NotFoundException
   - ConflictException
   - RateLimitExceededException 等

4. システムエラー（サーバ内部エラー）
   - DataAccessException / QueryTimeoutException 等（Spring Data 系）
   - MailException 等（メール送信失敗）
   - その他 RuntimeException

### 3.2 カスタム例外クラスの基本方針

- ドメインエラーは原則としてカスタム例外で表現する。
- カスタム例外には最低限以下の情報を持たせる。
  - エラーコード（例: USER_NOT_FOUND, INVALID_TOTP_CODE）
  - ユーザー向けメッセージ（ローカライズのキー or メッセージ）
  - ログ用詳細メッセージ（オプション）
- エラーコードは API 仕様で定義される ProblemDetail の detail / extensions と対応させる。

### 3.3 HTTP ステータスとの対応

代表的なマッピングルールは以下とする。

- 400 Bad Request  
  - 入力不備（バリデーション）  
  - ドメイン的に不正な要求（例: 無効な状態遷移）

- 401 Unauthorized  
  - 認証失敗（ログイン失敗 / セッション無効 / MFA 未完了など）

- 403 Forbidden  
  - 認証は成功しているが、権限不足 / AMR 不足

- 404 Not Found  
  - ユーザーやセッションなど対象リソースが存在しない

- 409 Conflict  
  - 既に登録済み / 状態競合（例: すでに TOTP 有効化済み 等）

- 429 Too Many Requests  
  - 一定回数以上の認証失敗など、レート制限に相当するケース

- 500 Internal Server Error  
  - 上記に分類できないサーバ内部エラー

実際の HTTP ステータスは API 仕様の定義を優先する。

## 4. サービスインターフェースと例外契約

### 4.1 AuthService

- ログイン関連メソッド  
  - 認証失敗 → UnauthorizedException  
  - 入力不備（フォーマット等） → BadRequestException  
  - アカウントロック等 → ForbiddenException または TooManyRequestsException（仕様に従う）

- トークンリフレッシュ関連  
  - 不正なリフレッシュトークン → UnauthorizedException  
  - 失効済みトークン → UnauthorizedException

### 4.2 MfaService

- TOTP / Email OTP / Recovery 各メソッドは、インターフェースコメントに従い

  - コード不一致・期限切れ → UnauthorizedException または BadRequestException（仕様で統一）
  - 挑戦 ID 不正 → BadRequestException
  - 認証コンテキスト不正（ログイン前など） → UnauthorizedException

### 4.3 SessionService

- listSessions / getCurrentSession  
  - 対象ユーザーが不正 → UnauthorizedException  
  - セッション ID 不正 → NotFoundException または BadRequestException（仕様に従う）

- logout / deleteById  
  - 対象セッションが既に削除済み → NotFoundException  
  - 他ユーザーのセッション ID → ForbiddenException

### 4.4 ポート（PasswordPort, TokenFacade など）

- PasswordPort  
  - verify で認証失敗 → 戻り値 false（例外は投げない）  
    - AuthService 側で UnauthorizedException にマッピング  
  - 想定外エラー（ハッシュアルゴリズム不明など） → RuntimeException（上位で 500）

- TokenFacade  
  - 不正トークン（署名不正等） → 専用例外（例: InvalidTokenException）  
    - AuthService / MfaService が UnauthorizedException に変換  
  - ストレージ障害 → RuntimeException（上位で 500）

ポート層では「技術的なエラー」と「ビジネスロジック上のエラー」を意識して、後者はできるだけサービス層のカスタム例外へ変換する。

## 5. コントローラー層の例外ハンドリング

### 5.1 GlobalExceptionHandler の役割

- Spring Boot 3 の ProblemDetail を利用し、全 API のエラーレスポンスを統一する。
- ハンドリング対象:
  - カスタム例外（BadRequestException 等）
  - 認証系例外（UnauthorizedException 等）
  - バリデーション例外（MethodArgumentNotValidException 等）
  - システム例外（RuntimeException 等）

### 5.2 レスポンスフォーマット

ProblemDetail をベースに、以下の情報を含める。

- type: エラー種類を表す URI（例: /problems/auth/invalid-credentials）
- title: 短いエラーメッセージ（ユーザー向け）
- status: HTTP ステータスコード
- detail: 詳細説明（必要に応じて）
- instance: 対象リクエストのパス
- extensions:
  - errorCode: システム内のエラーコード（例: AUTH_INVALID_CREDENTIALS）
  - fieldErrors: フィールド単位バリデーションエラー（400 の場合）

内部ログにはスタックトレースを残すが、レスポンスには含めない。

## 6. ログ・監視方針

- 4xx 系（クライアントエラー）  
  - WARN レベルでログ出力（必要に応じて情報量を抑える）

- 5xx 系（サーバエラー）  
  - ERROR レベルでログ出力し、スタックトレースを記録

- セキュリティ関連  
  - 認証失敗回数が一定閾値を超える場合、統計情報として監視対象  
  - トークン検証失敗なども必要に応じて監視連携

ログメッセージには、個人情報・機微情報（パスワード・トークン全体など）を含めない。

## 7. テストとの関係

- 単体テスト（UT）  
  - サービスインターフェースが仕様通りの例外を投げることを確認  
  - ポートをモックし、想定エラーを注入して例外マッピングを検証

- 結合テスト（IT）  
  - inmem / Cassandra プロファイルで、Repository 実装から発生しうるエラーが  
    想定されたカスタム例外 or HTTP ステータスに変換されることを確認  
  - 例: データ整合性違反 → ConflictException → HTTP 409

- E2E テスト  
  - 実サーバ（spring-boot:start）を起動し、  
    実際の ProblemDetail（status / type / errorCode）を検証

テストポリシー（00_テストポリシー.md）側のマトリクスには、

- 各 API の正常系・エラー系  
- サービスの想定例外

を整理し、本ポリシーと整合を取る。

## 8. 運用・拡張ルール

- 新たな API / ドメイン機能追加時は、  
  - 本ポリシーに従ってエラーケースを列挙し、  
  - 必要に応じて新しいカスタム例外・エラーコードを定義してから実装する。

- 例外クラス追加や変更を行う場合、
  - 本ポリシー（例外・エラー設計ポリシー）

  - [例外クラス一覧](04_例外クラス一覧.md)
  - [テストポリシー](../../テスト仕様/00_テストポリシー.md)

  の 4 文書に反映する。
