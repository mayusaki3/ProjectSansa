# 例外クラス一覧（Project Sansa / sansa-auth）

## 1. 目的

本書は、sansa-auth モジュールにおける「例外クラス」の一覧と役割を整理し、

- 実装で使用する例外クラスの種類
- 各例外クラスと HTTP ステータスの対応
- レイヤ（コントローラー / サービス / ポート・インフラ）ごとの責務

を明示することを目的とする。

本書は、以下の文書と連携する。

- 01_リポジトリ・ドメインモデル仕様.md
- 02_サービスポート仕様.md
- 03_例外・エラー設計ポリシー.md
- テスト仕様一式（UT / IT / E2E）

---

## 2. スコープ

- 対象モジュール
  - sansa-auth（Webサービス / 認証・セッション (M01)）
- 対象レイヤ
  - コントローラー層（REST API）
  - サービス層（AuthService / MfaService / SessionService / WebAuthnService など）
  - ポート・インフラ層（TokenFacade / PasswordPort / Repository Port など）

本書では **「どの例外クラスを定義して使うか」** にフォーカスし、  
HTTP レスポンスフォーマットや ProblemDetail の詳細は 03_例外・エラー設計ポリシー.md に委ねる。

---

## 3. 命名・継承ポリシー概要

### 3.1 命名ルール

- ドメイン例外（クライアント起因の業務エラー）
  - `BadRequestException`, `UnauthorizedException`, `ForbiddenException`,  
    `NotFoundException`, `ConflictException`, `TooManyRequestsException` など
- 技術例外（トークン検証等の技術的エラー）
  - `InvalidTokenException` 等
- 共通ルール
  - クラス名は **用途 + Exception** とし、HTTP ステータスと対応付けできる名前とする
  - 例: `BadRequestException` → HTTP 400, `ConflictException` → HTTP 409

### 3.2 継承関係（方針）

- すべてのカスタム例外は `RuntimeException` を継承する
- 必要に応じて、認証ドメイン用の基底クラスを導入可能とする
  - 例: `AuthDomainException extends RuntimeException`
  - 上記の下に `BadRequestException` などをぶら下げる設計も許容

実装の段階で、基底クラス導入の要否を検討し、本書に追記する。

## 4. 例外クラス一覧（共通）

### 4.1 ドメイン例外（HTTP 4xx 系）

| クラス名                 | パッケージ案                     | 対応 HTTP ステータス | 主な用途 / 発生条件                                                                 |
|--------------------------|-----------------------------------|----------------------|--------------------------------------------------------------------------------------|
| `BadRequestException`    | `com.sansa.auth.exception`       | 400 Bad Request      | 入力フォーマット不正、必須項目欠落、期限切れコードなど、クライアント入力の妥当性違反 |
| `UnauthorizedException`  | `com.sansa.auth.exception`       | 401 Unauthorized     | 認証失敗、セッション無効、MFA 未完了など「未認証」状態                              |
| `ForbiddenException`     | `com.sansa.auth.exception`       | 403 Forbidden        | 認証は成功しているが、権限不足 / AMR 不足などのアクセス拒否                         |
| `NotFoundException`      | `com.sansa.auth.exception`       | 404 Not Found        | ユーザー・セッション・MFA 情報など、対象リソースが存在しない                        |
| `ConflictException`      | `com.sansa.auth.exception`       | 409 Conflict         | 既に登録済み、状態競合（例: 既に TOTP 有効化済みのユーザーに再登録要求）           |
| `RateLimitExceededException` | `com.sansa.auth.exception` | 429 Too Many Requests | レート制限超過（ログイン試行・MFA 試行・OTP 送信など） |

#### 備考

- 上記は **サービス層が投げる主な例外クラスのセット** として位置付ける
- 各 API 仕様で定義される ProblemDetail の `type` / `status` / `errorCode` と  
  一貫性を保つことを前提とする
- ドメイン固有の詳細エラー（例: `PreRegistrationExpiredException` 等）が必要になった場合は、  
  本一覧に追記する

---

### 4.2 技術例外（ポート・インフラ層）

| クラス名                 | パッケージ案                     | レイヤ      | 主な用途 / 発生条件                                                                       |
|--------------------------|-----------------------------------|------------|-------------------------------------------------------------------------------------------|
| `InvalidTokenException`  | `com.sansa.auth.exception`       | ポート層   | トークンの署名不正、期限切れ、形式不正など、トークン検証失敗時に TokenFacade などが利用 |
| （Spring 標準例外群）    | `org.springframework.dao.*` 他   | インフラ層 | DataAccessException / QueryTimeoutException 等、DB 由来のシステムエラー                  |
| （Mail 送信例外）        | `org.springframework.mail.*`     | インフラ層 | MailException 等、メール送信の失敗                                                       |

#### マッピング方針（概要）

- `InvalidTokenException`
  - サービス層で `UnauthorizedException` に変換し、HTTP 401 として返却
- DataAccessException / MailException など
  - 原則として **システムエラー（5xx）** として扱い、  
    GlobalExceptionHandler で HTTP 500 にマッピングする

## 5. レイヤ別の使用ルール

### 5.1 コントローラー層（REST Controller）

- 原則として **カスタム例外を直接投げない**
  - サービス層・ポート層から投げられた例外を受け取り、  
    GlobalExceptionHandler で ProblemDetail に変換する
- コントローラー層で発生しうる例外
  - バリデーション系
    - `MethodArgumentNotValidException`
    - `ConstraintViolationException`
  - JSON パース系
    - `HttpMessageNotReadableException`
  - これらは 03_例外・エラー設計ポリシー.md に従って 400 系へマップ

### 5.2 サービス層（AuthService / MfaService / SessionService / WebAuthnService）

- クライアント起因の業務エラー:
  - → 本書 4.1 のドメイン例外を投げる（`BadRequestException` 等）
- 認証・認可エラー:
  - → `UnauthorizedException` / `ForbiddenException`
- リソース不在:
  - → `NotFoundException` または `BadRequestException`（API仕様で統一）
- ポート層からの技術エラー:
  - `InvalidTokenException` などを受け取り、`UnauthorizedException` へ変換
- レート制限違反:
  - → `RateLimitExceededException`
  - 判定責務はサービス層に置く
  - ポート層は「回数・期限」等の情報のみを返却する

### 5.3 ポート・インフラ層（TokenFacade / PasswordPort / Repository Port 等）

- ポート層の役割
  - 技術的エラー（DB 接続、トークン署名検証、メール送信など）を検知する
  - ドメイン判断は可能な限りサービス層へ委譲する
- 使用例外（方針）
  - トークン検証系エラー → `InvalidTokenException`
  - DB / メール系 → Spring の標準例外（DataAccessException, MailException 等）
  - サービス層はこれらを捕捉して「ドメイン例外」へマッピングする

## 6. 今後の拡張・運用ルール

- 新たなドメイン機能を追加する際は、
  - まず 03_例外・エラー設計ポリシー.md に従ってエラーケースを列挙
  - 本書に新規例外クラス（例: `PreRegistrationExpiredException`）を追記
  - サービスポート仕様（02_サービスポート仕様.md）に「どのメソッドが何を投げるか」を明記
- 既存例外クラスを変更 / 廃止する場合は、
  - 本書（例外クラス一覧）
  - 03_例外・エラー設計ポリシー.md
  - 02_サービスポート仕様.md
  - テストポリシー / テストマトリクス

  を同時に更新する。
